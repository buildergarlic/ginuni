# 검증 가능한 AI 워크플로우 — 개발 구현

작성일: 2026-09-09. `v0.6.0-beta.1` 제한 파일럿 베타에 포함할 구현 설명이다. 파일럿 배포 승인은 아래의 실제 작가·방송 자료·한컴오피스 검증 기준을 통과했다는 뜻이 아니며, 태그와 설치본의 게시 상태는 GitHub Releases에서 별도로 확인해야 한다.

## 화면해설작가를 위한 사용법

1. **영상을 선택한다.** 사용 권리를 확인한다. 기본값인 내 PC 분석은 음성을 외부로 보내지 않는다. 다른 분석 방식은 추가 설정 안에 있다.
2. **대사 초안을 확인한다.** 영상을 보며 대사·화자·시간을 고치고, 해설 행에는 작가가 직접 화면해설을 쓴다. `다음 확인할 행`으로 이동하고 `선택한 행 확인 완료`를 누른다. 수정과 확인 완료는 다른 동작이다.
3. **대본을 저장한다.** 오류를 수정하고 HWPX 또는 SRT로 저장한다. SRT에는 대사만 들어간다. 확인 전 구간이 있으면 검수를 계속할지, 현재 내용을 작업용 파일로 저장할지 선택한다.

교정은 선택 사항이다. `사용 권리와 외부 전송 설정`에서 **대사 텍스트 전송**을 별도로 동의한 뒤 `선택한 대사 교정 요청 (유료)`를 누른다. 원문·제안·이유를 보고 적용하거나 거절한다. AI는 화면해설을 생성하지 않으며 대본을 자동 승인하지 않는다.

`이전 상태로 복구`에서 이전 저장본을 불러올 수 있다. 복구 직전의 내용도 별도로 남는다. `작업 기록 · 고급 정보`는 필요한 경우에만 펼쳐 본다.

오른쪽 대사·해설 내용 또는 현재 활성 편집창을 클릭하면 로컬 영상과 유튜브 영상이 그 행의 시작 시각으로 이동한다. 이 동작은 작성 중인 초안을 버리지 않으며, 일시 정지 중인 영상을 자동으로 재생하지 않는다.

## 설계도와 구현의 연결

| 설계 단계 | 구현 | 확인 가능한 근거 |
|---|---|---|
| 입력 확인 | 권리 확인, 별도 음성/교정 동의, 음성 트랙·길이 확인 | 프로젝트 동의 시각, 원본/분석 음성 SHA-256 |
| 음성·화자 분석 | 기존 로컬/로컬 화자 분리/OpenAI 유지 | 실행 ID, 모델, 처리 파이프라인 버전, 구간 ID/원본 시간 |
| 검사 ① | 잘못된 응답·시간·텍스트 거부, 행 시간/구간 연결 검사 | 실행 checks, 작가 점검 목록 |
| 교정 제안 | 선택한 대사만 교정, 원문·교정문·이유·모델/프롬프트 버전 보존 | 제안 상태, 적용/거절 시각, 수정 전후 |
| 작가 확인 | 명시적인 확인 완료, 수정 시 확인 해제 | 로컬 승인 이벤트, 행 승인 시각 |
| 검사 ② | 시간 오류 차단, 미확인 경고, HWPX XML/행 내용·SRT 내용 검사 | 출력 검사 성공 후 파일 SHA-256 |
| 버전 저장 | 기존 버전 파일 보존, 출력 원본 실행 추적 | exports와 검증 기록 JSON |
| 실패·복구 | 분리된 초안에서 분석, 실패/취소/충돌 시 기존 대본 보존, 최근 10개 복구본 | 실행 결과, 복구 전/분석 전/교정 전/출력 전 스냅샷 |
| 개발자 모델 평가 | 권리·정답 검수·모델 설정·자료 분리 선언과 정답 기반 로컬 평가 | 별도 평가 JSON, 통과해도 자동 모델 교체 없음 |

핵심 구현 파일은 `src/shared/workflow.ts`, `src/main/services/analysis-workflow.ts`, `project-store.ts`, `correction.ts`, `export-workflow.ts`, `evaluation.ts`, `src/renderer/src/WorkflowPanel.tsx`다.

## 중요한 안전 정책

- 분석 결과를 기존 프로젝트에 바로 덮어쓰지 않는다. 응답 검사를 통과하고 분석 중 대본이 바뀌지 않았을 때만 새 초안을 적용한다.
- 기존 프로젝트의 `reviewed`는 과거에 편집만 해도 켜지던 값이다. 처음 업그레이드로 열 때 새 워크플로우에서는 **확인 전으로 이관**한다. 대사와 작가 작성 내용은 유지한다.
- 원본 인식 구간과 과거 실행의 구간을 보존한다. 교정 적용은 표시된 원문과 현재 행이 같을 때만 허용하며 다시 확인 전 상태가 된다.
- 한 프로젝트의 저장 작업은 차례로 처리하고 revision 충돌을 검사한다. 복구·교정·출력 중 편집은 잠시 잠긴다.
- 복구본은 행·제안·구간 JSON이며 영상/음성을 복제하지 않는다. 최신 10개를 유지한다. 손상된 복구본 하나가 정상 복구본 사용을 막지 않으며 손상 파일은 자동 삭제하지 않는다.
- 외부 전사 요청은 호환성 문제에 한해 같은 공급자로 **1회만 추가 시도**하며 진행 메시지로 알린다. SDK의 숨은 재시도는 끈다. 요청별 제한 시간은 10분이다. 입력은 기존 3시간/24.5MB 제한을 따른다.
- 외부 교정 요청은 최대 20행·12,000자, 60초, 재시도 없음, 출력 길이 제한이다. 현재 작가 화면에서는 선택한 1행만 보낸다. 공급자 전환, 자료 자동 수집·전송·학습은 하지 않는다.
- 요청 수·입력량 제한은 무한 재시도와 예상 밖 사용량을 줄이는 장치다. 실제 청구액은 공급자 요금·계정에 따른다. 앱에서 통화 기준 지출 상한을 보증하지 않는다.
- 검증 기록에는 민감한 대사·수정 이력이 들어간다. 기록 저장은 로컬 파일 내보내기이며 일반 문의용 진단 파일과 다르다. 공유 전 내용을 확인해야 한다.
- 대본과 검증 이력 JSON 자체는 암호화되지 않는다. API 키의 Windows 암호화 저장과는 구분되며, 기관의 파일 접근·보관 정책을 따라야 한다.
- 해시는 파일 동일성 확인 수단이며 전자서명·변조 불가능한 감사 장부가 아니다. `writer`는 로컬 작가의 동작 구분이며 본인 인증된 실명 서명이 아니다.
- 자동 점검과 다른 AI의 의견으로 의미적 정확도를 보증하지 않는다. 말소리 인식이 없다는 이유만으로 실제로 무음이라고 단정할 수 없으며, 해설 삽입 가능 여부는 작가가 원음을 듣고 판단한다.

## 재현 가능한 검증

```powershell
npm run verify
npm run evaluate:workflow -- docs/evaluation-example.json
```

평가 예제는 합성 문자열이다. 실제 성능 측정 결과가 아니다. CER/WER은 corpus 편집거리로 계산하고 미측정값은 null이다. DER/SubER는 별도 정답 주석과 외부 도구·버전·주석 출처가 있을 때 입력받는 값이며 앱이 자체 계산했다고 주장하지 않는다.

실제 Electron 회귀 확인 스크립트는 `scripts/qa-workflow.mjs`다. `npm run build` 후 Playwright가 설치된 개발 환경에서 `node scripts/qa-workflow.mjs`로 실행한다. 번들 Playwright를 쓰는 경우 `GINUNI_PLAYWRIGHT_MODULE`에 해당 패키지의 `index.mjs` 절대 경로를 지정한다.

이 스크립트는 별도 임시 문서/설정 폴더, 합성 무음, 합성 대본을 만든다. 실제 사용자 프로젝트나 키를 쓰지 않는다. 실 API 호출 없이 실제 Electron 화면→IPC→프로젝트 파일→HWPX/SRT 출력을 점검하며, 출력은 `output/playwright`의 테스트 화면과 콘솔 점검 결과다. 파일 선택 대화상자 응답은 테스트 내에서 대신 제공한다. 실제 방송 자료나 실제 작가의 사용성 승인을 대신하지 않는다.

### 이번 구현의 확인 결과

- `npm run verify`: 테스트 222개(29개 파일), 타입 검사, 프로덕션 빌드 통과.
- 실제 Electron 점검 8개 통과, 화면 실행 오류 없음. 칸을 벗어나지 않은 편집의 자동 저장, 로컬 영상의 편집창 클릭 이동, 명시적 확인, 교정 적용과 원본 보존, 복구, HWPX/SRT 출력, 출력 후 계속 편집을 점검했다.
- 유튜브 메시지 경계 점검 4개와 실제 공개 유튜브 영상 점검 4개 통과. 대사·해설 행 선택과 활성 편집창 클릭이 실제 영상의 시작 시각으로 이동하며 일시정지·초안을 유지했다. 공개 IFrame API 예제 영상 `M7lc1UVf-VE`만 사용했고 음성 다운로드나 AI 분석을 하지 않았다.
- 합성 평가 예제 실행 성공. 실제 방송 음성이나 유료 API의 정확도·연결 성공을 의미하지 않는다.
- 개발용 Windows 폴더 빌드 성공. 패키지에 들어간 메인 코드가 위에서 검사한 빌드와 바이트 단위로 일치함을 확인했다.

`scripts/qa-youtube-seek.mjs`는 외부 유튜브 메시지 경계만 대체하는 점검이다. 같은 스크립트에 `--live`를 붙이면 실제 공개 유튜브 영상을 사용하는 선택적 점검이다. 두 결과는 구분하며 실제 방송 자료 평가나 전체 사용성 검증을 대신하지 않는다.

## 초기 개발용 실행 파일

처음 만든 개발 빌드는 `release/verified-workflow-dev-20260909/win-unpacked/화면해설 대본 도구.exe`다. **`win-unpacked` 폴더 전체를 함께 보관**해야 하며, 실행 파일만 옮기면 안 된다. 이 초기 빌드는 이번 유튜브 클릭 이동 수정 전의 보관본이므로, 파일럿에는 GitHub Releases의 `v0.6.0-beta.1` 설치본을 사용한다.

이 파일은 코드 서명되지 않은 개발용 빌드이며 공개 릴리스가 아니다. 실행 파일의 SHA-256은 `C51962A31274270A87BB4715BA7769BF21A1C749A1D62DFEB8A917174735D7F5`다. 실제 작업 자료를 열기 전에는 기존 프로젝트 폴더를 별도로 백업하고 시험용 프로젝트부터 확인한다.

## 아직 별도 확인이 필요한 사항

- 실제 한국어 방송 자료를 사용한 모델별 정확도·비용·처리시간 측정과 정답 평가 세트 구축.
- 화면해설작가 5–8명의 첫 사용·오류 복구·납품 동선 사용성 시험.
- 실제 OpenAI 계정의 유료 전사/교정 연결, 한컴오피스에서 긴 문서의 페이지 나눔·서식 확인.
- `v0.6.0-beta.1` GitHub Actions 설치본의 실제 서명 상태와 기존 베타 설치본에서의 자동 업데이트 확인. 인증서가 없으면 무서명 파일럿 베타와 SmartScreen 가능성을 명시한다.

## 구현 과정에서 정한 범위

- 프로젝트의 직접-main 정책에 따라 기존 개발 폴더에서 작업했다. 작업 트리를 분리하면 유일한 개발 원본 정책과 어긋나므로, 변경 충돌은 파일별 소유권과 revision 검사로 관리했다.
- 독립적인 파일 영역은 병렬 작업했고 공통 인터페이스는 먼저 확정했다. 잘못된 경계 판단의 비용은 통합 수정이므로 타입·회귀·실제 앱 검증을 추가했다.
- 이번 범위는 승인된 검증 워크플로우다. 과거 12주 로드맵의 사용자 연구·새 공급자 평가·배포까지 완료했다고 보지 않는다. 현장 검증 결과에 따라 후속 수정이 필요할 수 있다.
