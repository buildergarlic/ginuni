# 기누니 외화 화면해설 작업 대응 설계

작성일: 2026-09-15 · 상태: 검토용 설계 제안 · 기준: 현재 로컬 v0.6.0-beta.3 소스

**최우선 제약은 ‘이번 주 바로 사용’이다.** 9월 말 시험 사용 가정은 폐기한다. 첫 사용 가능한 후보는 9월 17일 목요일, 작가 PC에서 확인한 제공 목표는 9월 18일 금요일로 잡는다. 이 날짜는 개발 계획이며, 실제 영상·자막 미수령 상태에서 다섯 편의 추출·검수 완료까지 보장하는 날짜가 아니다.

이 문서는 프로그램 수정과 기능 추가의 설계이다. 앱 구현, OCR 실행, 정확도 측정, 실제 작품 처리, 배포는 수행하지 않았다. 동반 문서: [이번 주 실행 계획](../plans/2026-09-15-biff-this-week.md).

## 1. 판단과 권장안

이번 주에는 **기누니의 자막 가져오기·검수·출력 기능을 완성하고, 영상에만 자막이 있는 작품은 개발자 지원으로 SRT를 만들어 연결하는 방식**을 권장한다. 작가가 직접 실행하는 통합 OCR, 다국어 자동 번역, 시간 없는 대본의 자동 정렬까지 모두 같은 주에 완성하는 계획은 피한다.

‘OCR 기능이 있는 프로그램’과 ‘작가가 이번 주 작품 작업을 시작할 수 있는 상태’는 서로 다른 납품 항목이다. 이번 주 제공물에 지원 담당자가 만드는 SRT가 포함되는지 명확히 설명한다. **사용자가 원하는 조건이 지원 인력 없이 앱 하나로 모든 영상을 자동 처리하는 것이라면, 실제 샘플 검증 전에는 이번 주 완료를 약속할 수 없다.**

| 접근 | 이점 | 한계 | 결정 |
|---|---|---|---|
| 자막 가져오기 + 개발자 지원 OCR + 작가 검수 | 기존 편집·HWPX·SRT를 재사용하며 공식 한국어 표현 유지 | 영상만 받으면 별도 추출·검수 담당 필요 | 이번 주 권장 |
| 앱 내 OCR·번역·자동 정렬을 한꺼번에 구현 | 장기적으로 스스로 처리 가능 | 실행 파일 배포, 장편 처리, 자막 경계, 번역 품질을 동시에 검증해야 함 | 후속 단계로 분리 |
| 외국어 음성 인식→한국어 번역 우선 | 한국어 자막이 전혀 없는 작품의 보조 경로 | 상영 자막과 문구·구간이 달라지고 화면 문자 누락 가능 | 해당 작품에 한해 별도 검증 |

## 2. 고객이 받는 자료별 처리

| 받은 자료 | 이번 주 대응 | 정확히 설명할 한계 |
|---|---|---|
| 영상 + 한국어 SRT | 자막 가져오기→싱크 확인→해설 작성→HWPX/SRT | 해당 영상과 같은 편집본인지 확인 필요 |
| 영상 안에 선택 가능한 텍스트 자막 트랙 | 지원 담당자가 트랙을 추출하여 SRT로 제공 | 화면에 보이는 자막이 모두 하드자막인 것은 아님. 트랙 선택 UI는 후속 |
| 영상 화면에만 한국어 자막 | 지원 담당자가 표본 OCR→추출본 검수→SRT 제공 | 파일 가져오기만으로 해결되지 않음. 샘플과 처리·검수 시간이 필요 |
| 이미지형 자막 트랙(PGS/VobSub 등) | 트랙 종류 확인 후 이미지 OCR 지원 경로로 분류 | 텍스트 트랙처럼 단순 SRT 변환된다고 약속하지 않음 |
| 시간 있는 텍스트 대본 | 지원 담당자가 명확한 시간 표기를 SRT로 정리 | 타임코드 형식·영상 기준점 확인 |
| 시간 없는 한국어 대본 | 문단 원문을 보존하고 기존 편집 화면에서 대사 붙여넣기·시작/종료 지정 | 문장마다 정확한 시간은 텍스트만으로 알 수 없음 |
| 시간 없는 원어 대본 | 이번 주는 수동 연결. 후속으로 같은 언어 음성 인식 결과와 정렬 | 대본에 삭제 장면·누락 대사가 있으면 자동 정렬 실패 가능 |
| 외국어 음성만 있음 | 실제 언어 표본으로 원어 전사→번역 보조 처리 가능성을 판단 | 공식 한국어 자막 복원과 다름. 언어 검수자 필요 |
| DCP·재생 제한 자료만 있음 | 같은 편집본의 작업용 MP4와 자막 자료 요청 | 이번 주 앱의 직접 입력 범위는 재생 가능한 로컬 작업용 영상 |

텍스트 파일은 사용할 수 있다. 다만 **내용 활용 가능 여부와 정확한 시간 자동 부여 가능 여부를 분리해서 답변**해야 한다. 한국어 번역 대본을 외국어 음성에 같은 언어의 강제 정렬 방식으로 직접 맞추는 것은 지원 약속에 포함하지 않는다.

## 3. 현재 코드에서 확인한 사실

| 항목 | 현재 상태와 근거 | 설계 영향 |
|---|---|---|
| 기본 작업 흐름 | 영상 재생, 행 편집, 검수, 자동 저장·복구, HWPX/SRT 출력 존재 | 기존 Atelier 화면을 중심으로 확장 |
| SRT | `src/main/services/srt.ts:45`의 `buildSrtContent`는 출력만 수행. `AppApi`에 import 없음 | 가져오기 기능 신설 |
| 분석 언어 | `src/main/index.ts:220`에서 `language: 'ko'` 고정 | 외국어는 언어 선택·전달 경로 수정 필요 |
| 행 생성 | `src/shared/rows.ts:71` 이후 초 단위 내림/올림·최대 60초 병합 | 자막 전용 생성 함수로 우회 |
| 시간 표시·출력 | `src/shared/timecode.ts:9`, `src/main/services/srt.ts:5`는 이미 밀리초 지원 | 시간 엔진 전면 재작성 불필요. HWPX 간격 열의 정수 초 표시는 검토 |
| 공백 문구 | `src/shared/constants.ts:24`는 ‘사람 목소리 없음’을 단정 | 자막 없음과 무음 구별. 새 자막 경로에서는 사용 금지 |
| 겹침 | `src/shared/workflow.ts:40`은 행 겹침을 오류로 취급 | 원본 자막 보존과 편집용 겹침 해결 정책 필요 |
| 저장·복구 | `project-store.ts:180`에서 행 필드 화이트리스트 복사, snapshot은 제한 필드 저장 | 새 출처 필드·자막 원본·시간 보정도 저장/복구에 포함 |
| 출처 추적 | `export-workflow.ts:12`는 ASR run의 `sourceSegments`만 찾음 | 자막 원본 큐도 출처로 해석하도록 확장 |
| 화자 표시 | `speaker-labels.ts:3`, `workflow.ts:32`는 OpenAI run을 화자 지원 근거로 사용 | 번역·가져오기를 ASR run으로 위장하지 않음 |
| 미디어 준비 | `media.ts:97`의 `prepareMedia`는 오디오 확인·추출까지 수행 | 자막 가져오기는 영상 정보 확인만으로 진행 가능하게 분리 |

조사는 소스 정적 검토이다. 저장소 README도 현재 파일럿을 실제 방송 정확도·장편 한컴 검증 완료판으로 설명하지 않는다. 기존 기능을 재사용하더라도 이번 작품과 작가 PC에서 연결 확인이 필요하다.

## 4. 이번 주 제품 범위

### 반드시 포함

1. **한국어 SRT 가져오기:** 파일 선택, 인코딩·문장·시간 미리보기, 오류 위치 표시, 적용 전 기존 대본 보존.
2. **자막별 시간 유지:** 기본은 자막 한 개당 대사 한 행. 밀리초·여러 줄·문장 순서 보존. ASR 병합 함수 사용 금지.
3. **영상과 시간 맞추기:** 전체 자막에 일정한 시간차를 적용하고 원상복구. 초반·중반·후반 비교 안내. 시간이 갈수록 어긋나면 일정 시간차로 해결했다고 표시하지 않음.
4. **대사·해설 직접 수정:** 기존 행 편집·분할·병합·검수·영상 이동 활용. 원본 연결을 유지하고 수정 시 검수 완료 상태 해제.
5. **기존 HWPX/SRT 출력:** 실제 검수한 대본을 출력. 원본 자막과 수정한 대본 자막의 차이를 명확히 안내.
6. **시간 없는 대본의 수동 사용:** 음성 분석 없이 영상 준비 후 편집을 시작할 수 있게 한다. 빈 프로젝트에도 ‘첫 대사 추가’를 제공한다. 임시 입력창에서 문단 붙여넣기와 현재 영상 시점으로 시작/종료 지정을 하고, 두 시간이 유효해진 뒤에 대사 행으로 저장한다. 아직 시간 지정 중인 문단을 임의 시간의 대사 행으로 만들지 않음.
7. **기존 프로젝트 보존:** 가져오기 실패·취소·충돌 시 기존 행과 해설을 유지. 저장·재열기·복구 회귀 확인.

SRT는 UTF-8/BOM과 UTF-16 BOM을 우선 지원한다. CP949/EUC-KR 자료는 명시적 인코딩 선택 또는 지원 담당자의 UTF-8 변환으로 처리한다. 자동 추정에 실패한 깨진 글자를 그대로 적용하지 않는다. 자막 스타일 태그는 허용된 텍스트 처리 규칙으로 변환하고, 원본 바이트와 원문을 보존한다. 태그를 HTML로 실행하지 않는다.

이번 주 겹치는 자막은 자동으로 자르거나 누락하지 않는다. 미리보기에서 겹친 그룹과 원문을 보여 주고, 지원 담당자가 시간 조정 또는 명시적 그룹 합치기를 수행한다. 그룹 합치기는 편집용 시작의 최솟값·종료의 최댓값·원문 줄바꿈 연결을 사용하고, 모든 원본 큐 ID를 남긴다. 원본 자료는 변경하지 않는다. 겹침 해결 전에는 새 초안 적용을 차단한다.

### 이번 주 지원 업무로 제공

- 작품별 자막 트랙 여부 조사와 텍스트 트랙의 SRT 변환.
- 영상에만 있는 한국어 자막의 OCR 표본 검사, 본편 추출, 사람이 수정한 SRT 준비.
- 시간 있는 텍스트나 다른 자막 포맷을 검수 가능한 SRT로 정리.
- 원어 음성만 있는 작품의 원어 전사·번역 표본과 사용 가능 여부 판단.

OCR 결과물을 받았다고 모든 대사와 시간이 검수 완료된 것으로 간주하지 않는다. 지원자가 확인한 범위를 기록하고, 작가는 영상과 함께 최종 확인한다. **개발자 한 명이 앱 구현과 장편 다섯 편의 전수 검수를 동시에 끝낸다는 인력 가정은 두지 않는다.**

### 후속 앱 기능

영역 지정·미리보기·본편 OCR·중단/재개, 원문 이미지 비교, 다국어 ASR/번역, 자동 정렬, 자막 트랙 직접 선택, VTT/ASS 정식 가져오기, 작품 일괄 작업은 순서대로 분리한다. 이번 주 핵심 흐름이 늦어지면 이 항목들은 출시 조건에 넣지 않는다.

## 5. 작가 화면과 작업 흐름

새 프로젝트에서 **‘자막 파일로 시작’ / ‘대사를 직접 입력’ / ‘음성에서 만들기’**를 선택한다. 이번 주 제공판에 실제 OCR 실행 기능이 없으면 활성화된 ‘영상 자막 자동 추출’ 버튼을 표시하지 않는다. 영상만 받은 작가는 지원 절차로 만든 SRT를 같은 가져오기 흐름에서 사용한다.

자막 가져오기 화면에는 처음 몇 문장, 자막 개수, 최초/최종 시간, 오류·겹침 개수, 자료 출처를 표시한다. ‘새 초안 적용’ 시 기존 작업 백업을 만든다. 기존 작성 해설을 새 자막에 조용히 덮어쓰지 않는다.

검수는 기존처럼 영상 왼쪽·대본 오른쪽을 유지한다. 필요한 추가 정보는 ‘제공받은 자막’, ‘영상에서 추출한 자막’, ‘직접 입력한 대사’라는 출처, 원본 보기, 시간 맞추기뿐이다. 자막 출처만으로 화자를 추정하지 않는다.

자막 없는 부분에는 필요할 때 **‘해설 후보 · 대사와 소리를 확인하세요’**를 표시한다. 자막 표시 구간과 실제 대사 구간이 다를 수 있으므로 영상 청취 없이 해설 가능으로 승인하지 않는다. 외화 자막을 한국어로 읽어 주는 대사 낭독까지 납품 범위라면, 낭독 소요 시간과 해설 충돌은 추가로 작가가 배치해야 한다. 이번 주 자동 낭독 시간 배분은 범위 밖이다.

## 6. 데이터와 시간 설계

### 이번 주 최소 확장

영상의 `SourceKind = local | youtube`는 유지한다. 자막은 별도 자료다. 앱 스키마는 2→3으로 명시적 마이그레이션하며 기존 workflow version 1은 유지한다.

| 추가 개념 | 필수 정보 | 원칙 |
|---|---|---|
| `SubtitleWorkspace` | version=1, 자료 목록, 활성 자료 ID, 원본 큐, 시간 보정값 | 프로젝트의 선택적 새 필드. 기존 프로젝트에는 빈 상태 |
| `SubtitleAsset` | id, 파일 해시, 파일명, 인코딩, 가져온 시각, 언어, sourceKind=`provided-srt`/`ocr-srt`, declaredAuthority | 제공자 주장과 실제 검수 결과를 구별. OCR SRT를 공식 자막으로 승격하지 않음 |
| `SubtitleCue` | id, assetId, 원래 순번, startMs, endMs, text | 원본 불변. 반개구간 `[startMs,endMs)` |
| `ScriptRow.sourceCueIds` | 연결된 원본 큐 ID 목록 | 현재 `sourceSegmentIds`와 함께 저장·검증·복구. 분할하면 양쪽 모두 원본 참조 유지 |
| 시간 보정 | assetId, offsetMs, 적용 이력 | 원본 시간 기준으로 계산. 반복 열기·적용에서 중복 더하기 금지 |
| 가져오기 기록 | id, assetId, 시간, 입력 해시, 결과, 원본/적용 행 수, 겹침 해결값·변경 이유 | 기존 ASR `runs`와 분리. 출처 내보내기가 두 경로 모두 해석 |

이번 주 편집본의 정본은 `project.rows`다. 불변 원본 자막 큐와 별개로 또 하나의 변경 가능한 자막 정본을 만들지 않는다. 기본 1큐→1행이라 기존 SRT 직렬화도 밀리초를 유지한다. 작가가 행을 합치거나 나누면 **‘편집 대본 SRT’**에 그 변경이 반영되고, 처음 제공받은 SRT와 동일한 파일이라고 주장하지 않는다.

시간 보정은 가져오기 전 미리보기에서 먼저 제공한다. 적용 후 재조정 시 현재 편집 행을 대상으로 전체 이동·선택 행 이동을 구별하고 백업·검수 해제를 수행한다. 원본 기반 재가져오기는 별도 새 초안이다. 작품 전체가 서로 다른 편집본이면 자동 시간 보정 대상으로 취급하지 않는다.

원본 자막의 겹침은 자료로 보존하되 이번 주 편집 행은 기존 비겹침 규칙을 유지한다. 향후 다중 자막 트랙이 필요할 때 원본·작업 큐 트랙과 화면해설 배치 트랙을 분리한다. 전역 겹침 검사를 삭제하는 방식으로 해결하지 않는다.

검사 순서는 원본 구문·시간의 유효성 확인 → 시간차·명시적 겹침 해결값 적용 → 실제 영상 범위와 편집 행 겹침 확인이다. 01:00:00부터 시작하는 자막을 1시간 넘는 시간이라는 이유로 보정 전에 거부하지 않는다. 보정 후 음수·역전·영상 밖으로 나가는 행은 적용하지 않는다.

### 후속 확장

`DialogueTrack`으로 공식 자막, OCR, 원어 ASR, 한국어 번역을 분리한다. 각 트랙에 언어, 부모 트랙, 원본 자료, 취득 run, `timingBasis`(화면 표시/발화/수동), 검수 상태를 둔다. 번역 문장에는 부모 원어 ID를 유지하며, 표시 시간·발화 시간·해설 배치 시간을 각각 보존한다.

비디오의 프레임 PTS와 시간 기준을 사용한다. 가변 프레임 영상에 프레임 번호÷평균 FPS를 적용하지 않는다. 시작 타임코드가 01:00:00인 자료도 앱 내부에서는 영상 시작 기준 밀리초로 정규화하고 원래 시작값을 보존한다. 후속 선형 싱크 보정은 `영상시간 = a × 자막시간 + b`로 계산하되 두 기준점을 맞춘 뒤 제3의 시점에서 검증한다. 편집 차이로 구간별 어긋남이 발생하면 구간 재연결 또는 동일 편집본 요청으로 처리한다.

## 7. OCR 설계와 이번 주 적용 판단

우선 검증 후보는 **RapidOCR + ONNX Runtime CPU + 한국어 PP-OCRv5 인식 모델**이다. RapidOCR는 Paddle 계열 OCR 모델의 실행 도구이며, 두 이름을 완전히 다른 인식 모델로 비교하지 않는다. 한국어는 `korean_PP-OCRv5_mobile_rec`를 명시해야 한다. 한국어 모델 지원 사실은 [PaddleOCR 모델표](https://www.paddleocr.ai/main/en/version3.x/module_usage/text_recognition.html)와 [RapidOCR 지원표](https://rapidai.github.io/RapidOCRDocs/main/model_list/)에서 확인했다. 이는 영화 자막 정확도 보증이 아니다.

이번 주는 개발 환경의 별도 작업 도구로 표본을 검증해 SRT를 만들고 기누니에 연결한다. 작가에게 Python 설치를 요구하지 않는다. 후속 앱 통합에서는 OCR를 별도 프로세스로 실행하고 패키지·검출 모델·한국어 인식 모델·문자 사전·SHA-256을 고정한다. GPU는 필수가 아니다. 네트워크가 없는 첫 실행까지 확인한다. [오프라인 모델 설정](https://rapidai.github.io/RapidOCRDocs/main/install_usage/rapidocr/how_to_use_offline_model/)

처리 단계:

1. 영상 정보·자막 트랙 유무·재생 가능 여부 확인. 추출 가능한 텍스트 트랙은 OCR 이전에 사용한다.
2. 하단 자막 영역 기본 제안 후 담당자가 영역 확인. 상단·여러 영역·두 줄·검은 여백 사례는 별도 확인한다.
3. 짧은 미리보기에서 한국어 인식과 처리 시간을 측정한다.
4. 본편은 연속 프레임의 자막 영역 변화 검사와 주기적 OCR을 함께 사용한다. 모든 프레임을 이미지 파일로 저장하지 않는다.
5. 같은 문장의 관측값을 시간 연속성·글자·영역으로 합치고, 빈 화면 이후 재등장한 같은 문장은 별도 큐로 둔다. 숫자나 부정어 한 글자만 바뀐 문장을 합치지 않는다.
6. 등장·소멸 경계를 주변 원본 프레임으로 다시 확인한다. 단순 1초 간격 추출을 정밀 모드로 사용하지 않는다. 빠른 미리보기 표본 사이에 짧은 자막이 통째로 빠질 수 있다.
7. 원문 이미지와 후보 문장, 낮은 신뢰도·페이드·불명확한 경계를 검수 대상으로 보존한다. 인식 실패를 자막 없음으로 처리하지 않는다.
8. 지원 담당자가 누락·중복·인명·숫자와 시간을 확인한 SRT를 만든다.

타임스탬프의 프레임 정보는 [ffprobe 문서](https://ffmpeg.org/ffprobe.html), 샘플링 시 프레임 삭제·복제 특성은 [FFmpeg fps 필터](https://ffmpeg.org/ffmpeg-filters.html#fps)를 근거로 한다. 실제 연속성 판단·병합 기준은 이 프로젝트에서 검증할 설계다.

한글 폰트, 테두리, 밝은 배경, 움직임, 페이드, 1초 미만 자막, 워터마크, 화면 속 간판, 인명·숫자, 중첩 자막을 평가한다. Tesseract `kor`는 후보가 실패할 때의 비교 기준이며, 여러 OCR 엔진을 처음부터 제품에 모두 넣지 않는다. [Tesseract 한국어 자료](https://tesseract-ocr.github.io/tessdoc/Data-Files.html)

## 8. 외국어 전사·한국어 번역과 텍스트 정렬

후속 전사는 영상의 실제 원어를 선택하거나 자동 감지를 사용한다. 로컬 Whisper와 현재 클라우드 요청의 언어 전달을 수정하되, 모델별 언어 파라미터·출력 형식·시간 정보 지원을 확인한다. 언어 혼용은 구간별 검토 대상으로 둔다.

**한국어 번역은 원어 전사 다음의 별도 단계**다. Whisper의 번역 기능과 기존 오디오 번역 API를 한국어 번역기로 오해하지 않는다. 해당 번역 경로는 영어 번역을 제공한다. [Whisper 공식 설명](https://github.com/openai/whisper), [OpenAI 파일 전사·번역 안내](https://developers.openai.com/api/docs/guides/speech-to-text)

원어 텍스트, 한국어 번역, 부모 문장 ID, 원래 타임코드, 인명·호칭 용어집, 모델·프롬프트 버전을 보존한다. 번역은 문맥을 포함해 묶어서 수행하되 반환 ID의 누락·중복과 임의 시간 변경을 검사한다. 작가가 승인하기 전 원어·공식 자막을 덮어쓰지 않는다. 기존 맞춤법 교정 기능을 그대로 번역 버튼으로 쓰지 않는다.

장편 오디오는 적절한 길이로 나누고 원본 시간 오프셋을 합산한다. 클라우드 사용 시 요청 크기 제한, 경계 대사 중복, 재시도 횟수·비용 상한을 관리한다. 현재 기존 통합은 24.5MB를 상한으로 검사하므로 큰 영상 전체를 무조건 하나의 음성 요청으로 보내지 않는다. 오디오 전사 API의 25MB 제한은 [공식 문서](https://developers.openai.com/api/docs/guides/speech-to-text)에 명시되어 있다.

클라우드 번역은 기존 음성 전송·맞춤법 교정 동의와 별도로 텍스트 번역 전송 범위를 안내한다. 자료 외부 전송이 허용되지 않으면 로컬 OCR·로컬 전사와 사람 번역 경로를 사용한다. 이를 이유로 원문 전체를 임의로 외부 서비스에 보내지 않는다.

시간 없는 대본은 ‘미정렬’ 상태로 보존한다. 같은 언어 음성·대본에는 정렬을 제안할 수 있지만, 한국어 대본과 외국어 음성은 문맥 대응을 통한 후보 연결과 수동 기준점이 필요하다. 임의로 전체 영상 길이에 균등 배치해 정확한 타임코드처럼 출력하지 않는다.

## 9. 품질 기준과 사용 개시 조건

아래 수치는 **제안하는 통과 목표**이며 아직 측정하지 않았다. 모델의 자체 신뢰도 점수는 정답 확률로 표시하지 않는다.

| 대상 | 통과 조건 |
|---|---|
| SRT | 지원 입력에서 문구·줄바꿈·시작/종료 밀리초 100% 보존. 적용/저장/재열기/출력 왕복 확인. 의도한 태그 변환은 미리보기와 변경 기록으로 구별 |
| 시간 맞추기 | 초반·중반·후반 기준점 확인. 보정값 중복 적용 0건, 음수·역전·영상 밖 구간 차단. 다른 편집본을 일정 오프셋으로 해결 처리하지 않음 |
| 작업 보존 | 가져오기 실패·취소·편집 충돌·복구 시 작성 해설 및 원본 자료 손실 0건 |
| 첫 OCR 표본 | 첫 작품 5~10분, 가능하면 100개 이상 큐. 원본과 사람이 대조. 짧은 자막·밝은 배경 등 어려운 장면 포함 |
| OCR 본편 확대 | 작품별 별도 평가 구간에서 큐 재현율·정밀도 각각 98% 이상, 문자 오류율 2% 이하, 시작/종료 절대 오차 P95 200ms 이하를 잠정 목표로 평가 |
| OCR 기준 미달 | 전 자동 처리 승인 보류. 문제 영역 재설정·수동 복구 후 지원형으로만 제공. 누락을 검수 담당자에게 숨기지 않음 |
| 효과 | 동일 난이도 자료에서 추출+교정에 쓰는 사람 시간이 수작업보다 감소. 30% 절감을 초기 목표로 하되 측정 전 약속하지 않음 |
| 작가 제공판 | 실제 PC에서 본편 열기→자막 적용→수정→저장→재시작→HWPX/SRT 출력 성공. 한컴에서 첫/중간/마지막 페이지 확인 |
| 작품 납품 | 자동 생성과 별개로 전체 대사·시간·해설을 사람이 확인. 미확인/중요 오류가 남은 결과는 초안으로 구별 |

큐 재현율은 정답 자막 중 찾아낸 비율, 정밀도는 추출 자막 중 실제 자막인 비율이다. 놓친 자막을 평가 대상에서 빼지 않는다. 문자 오류율은 정답 전체에 대한 삽입·삭제·대치 비율이며, 정규화는 NFC와 공백 정책을 고정하고 숫자·부정어·문장부호를 유지한다. 시간 오차와 인식 문자 오류는 분리해서 측정한다.

설정 조정용 구간과 최종 평가 구간을 분리한다. 첫 작품의 성공을 다른 네 작품의 성공으로 간주하지 않는다. 자료를 받는 순서대로 각 작품의 초반·중반·후반과 자막 스타일을 확인한다. 저신뢰도 항목만 보면 누락된 자막을 발견할 수 없으므로 영상 구간 자체를 대조한다.

## 10. 이번 주 일정과 자원

| 날짜 | 앱 개발 주담당 | 자료 처리·검수 담당 | 종료 기준 |
|---|---|---|---|
| 9/15 화 | 입력 경로·최소 스키마·수정 파일 고정 | 첫 작품 영상/자막/샘플·길이·담당 작가 확보 | SRT 유무와 영상만 있는 경우의 담당 경로 결정 |
| 9/16 수 | SRT 미리보기·정밀 시간·가져오기·저장 연결 | 자막 트랙 조사, OCR 표본 및 처리시간 측정 | 시험 SRT가 기존 출력까지 연결 |
| 9/17 목 | 시간차 보정·수동 작업 시작·출처/복구·핵심 오류 수정 | 첫 작품 SRT 준비, 작가와 실제 구간 대조 | 첫 사용 후보판과 첫 작품의 사용 가능 구간 확보 |
| 9/18 금 | 실제 작가 PC 설치·작업·한컴 출력 확인 | 첫 작품 인계, 나머지 작품을 준비되는 순서대로 처리 | 사용 가능한 경로만 제공하고 사용법 안내 |

개발자 1명 기준 순수 앱 개발·검증은 약 3~4일을 계획 범위로 본다. 저장·출처·복구 회귀 또는 실제 자료 문제가 발생하면 시간이 더 필요하다. 자료 변환과 전수 검수는 별도 작업량이다. 수요일까지 첫 자료와 검수 담당자가 확보되지 않으면 금요일 목표는 앱 준비로 한정되며, 특정 작품의 사용 개시는 자료 확보·검증 이후가 된다.

공식 자막 없이 영상만 온 경우에도 OCR 표본과 앱 개발을 동시에 해야 한다. 인력이 한 명뿐이면 준비된 SRT의 앱 연결을 먼저 확보하고, OCR 지원·장편 검수 시간을 추가로 배정해야 한다. 금요일을 지키기 위해 전수 검수가 끝나지 않은 것을 완료로 표시하지 않는다.

## 11. 작업량과 비용 산정

개발비, OCR 실행비, 번역 API 비용, 사람 검수비, 설치·지원비를 분리한다. 로컬 OCR도 사람의 검수와 PC 처리 시간은 발생한다. 구체적인 단가는 협의되지 않았으므로 금액을 임의로 확정하지 않는다.

- 작품별 예상 기계 처리시간 = 표본의 `처리시간 ÷ 영상시간` × 본편 길이. 인코딩·검사·재실행 시간을 별도로 더한다.
- 사람 작업시간 = 표본 교정시간을 본편으로 환산 + 전체 누락 점검 + 고유명사·시간·출력 확인.
- 다섯 편 예상량 = 각 작품의 추정량 합계. 첫 작품 한 개의 인식률로 다른 작품을 단순 확정하지 않는다.
- 예시일 뿐인 계산: 120분×5편이면 총 10시간 영상이다. 측정된 처리 배율이 2라면 기계 처리만 20시간이며 사람 검수는 추가다.
- 임시 저장은 원본 프레임 전체 대신 대표 자막 이미지·검토 이미지·결과·체크포인트 중심으로 한다. 실제 압축 크기를 표본으로 측정하고 남은 디스크를 확인한다.

작품 시작 전에 받을 정보는 동일 편집본의 작업용 영상, 한국어 자막/대본 제공 가능 여부, 영상 언어, 시작 타임코드, 작품 길이, 작가 PC 사양, 자료 외부 전송 가능 여부, 첫 사용 시각, 검수 담당자다. 샘플은 선명한 장면 하나만 받지 말고 자막이 어려운 구간과 초반·중반·후반을 포함한다.

## 12. 결정과 범위 관리

이번 주 확정 제안은 **자막 파일 기반 작가용 기능 + 영상 자막의 지원형 추출 경로**다. 통합 OCR이 꼭 필요한 작품은 샘플 결과와 배포 검증을 본 뒤 추가한다. SRT가 없다는 이유로 음성 번역을 동일한 대체품이라고 설명하지 않는다.

후속 순서는 통합 OCR과 원문 비교·재개 기능 → 다국어 전사/한국어 번역 → 시간 없는 대본 정렬 → 다섯 편 일괄 관리다. 후속 단계의 날짜는 이번 주 표본 처리시간·작가 피드백과 실제 필요 경로에 따라 정한다. 새로운 자동화 기능 때문에 이번 주 기본 작업 경로 제공을 미루지 않는다.
